1. Tổng quan kiến trúc

Dự án được tách thành hai backend chính. Folder demo là backend nghiệp vụ thương mại điện tử, chịu trách nhiệm người dùng, sản phẩm, giỏ hàng, đơn hàng, thanh toán, ví, đánh giá, dashboard và quản trị. Folder ai-chatbot-service là service AI độc lập, chuyên xử lý chatbot, tìm kiếm ngữ nghĩa và gợi ý cá nhân hóa.

Client / Frontend -> Spring Boot REST API trong demo -> PostgreSQL: dữ liệu nghiệp vụ -> Redis: session/cache/blacklist token -> Flask AI service: chat, search, recommend -> Together AI: LLM + embedding -> PostgreSQL + pgvector: vector search và dữ liệu hành vi
Thành phần Vai trò Công nghệ chính

ai-chatbot-service Service AI độc lập cho chatbot, tìm kiếm thông minh và recommendation. Python, Flask 3.1.3, SQLAlchemy, Together AI, LangChain, pgvector, NumPy, Pydantic.
docker-compose.yml Chạy hạ tầng gồm PostgreSQL có pgvector, Redis, Spring backend và Flask AI. Docker Compose, image pgvector/pgvector:pg16, Redis 7 Alpine.

Điểm đáng nói khi bảo vệ

  • Hệ thống dùng kiến trúc tách service: nghiệp vụ chính tách khỏi AI để dễ phát triển, triển khai và mở rộng riêng.
  • Database PostgreSQL vừa lưu dữ liệu giao dịch, vừa dùng pgvector để lưu embedding phục vụ tìm kiếm ngữ nghĩa.
  • Spring Boot dùng mô hình nhiều lớp: Controller -> Service -> Repository -> Entity/Database.
  • AI service dùng pipeline: phân tích intent -> embedding/vector search -> lexical search -> rerank -> trả sản phẩm/chat.

4. Thuật toán và nghiệp vụ trong demo

4.1 Xác thực và phân quyền

SecurityConfig cấu hình hệ thống stateless, tắt CSRF cho REST API, dùng JwtAuthenticationFilter trước UsernamePasswordAuthenticationFilter. Một số endpoint public như đăng nhập, danh mục, thương hiệu, sản phẩm GET, VNPAY callback. Các endpoint còn lại yêu cầu authenticated hoặc @PreAuthorize.

Login thành công -> JwtUtils.generateAccessToken(user) -> roles được đưa vào claims -> client gửi Authorization: Bearer token -> JwtAuthenticationFilter kiểm tra chữ ký, hạn dùng, user, blacklist Redis nếu có -> SecurityContext có Authentication -> Controller/Service lấy user hiện tại để xử lý

4.2 Lọc sản phẩm động bằng Specification

ProductService.filterProducts dùng ProductSpecification để ghép điều kiện động: active, category, brand, khoảng giá, attribute values và sort. Với category, service thu thập cả danh mục con bằng đệ quy collectAllCategoryIds. Với thuộc tính, các value được gom theo attribute group.

Logic lọc thuộc tính: Trong cùng một nhóm attribute: OR Giữa các nhóm attribute khác nhau: AND Ví dụ: (màu = đỏ OR màu = xanh) AND (size = L OR size = XL)

4.3 Tạo sản phẩm có SKU và thuộc tính động

Khi tạo sản phẩm, service kiểm tra category/brand tồn tại, slug không trùng, attribute value không trùng, và attribute phải được phép dùng cho category đó. Ảnh sản phẩm được lưu theo thứ tự, ảnh đầu là thumbnail. SKU có mã riêng, giá riêng, tồn kho riêng và danh sách attribute value riêng.

4.4 Checkout preview

CheckoutService.preview không tạo đơn mà chỉ mô phỏng tổng tiền trước khi đặt hàng. Công thức tính:

subtotal = SUM(sku.price * quantity) shippingFee = shipping_method.cost discount = coupon discount hoặc shippingFee nếu coupon FREE_SHIPPING total = MAX(subtotal + shippingFee - discount, 0)

4.5 Đặt hàng và xử lý tồn kho

OrderService.placeOrder chạy trong transaction. Điểm quan trọng là trừ kho bằng câu update có điều kiện: chỉ trừ khi stockQuantity >= qty. Nếu số dòng update bằng 0 thì báo thiếu hàng và transaction rollback. Đây là cách tránh oversell tốt hơn so với chỉ check tồn kho trong RAM.

Đặt hàng: 1. Lấy cart và item được chọn 2. Validate stock 3. Tính subtotal, ship, coupon, total 4. Tạo Order PENDING + Payment UNPAID 5. Với từng item: atomic decrement stock 6. Lưu OrderItem 7. Nếu CASH: xóa item khỏi cart 8. Nếu VNPAY: tạo paymentUrl, chờ callback 9. Nếu WALLET: trừ ví, đánh dấu PAID, lưu lịch sử

4.6 VNPAY và idempotency

Thanh toán VNPAY có hai endpoint callback: return URL và IPN. Service kiểm tra transactionId, trạng thái đã PAID hoặc đơn đã CANCELLED để tránh xử lý trùng khi VNPAY gọi lại nhiều lần. Đây là tính idempotent: cùng một callback gọi lại không làm sai dữ liệu.

4.7 Dashboard

DashboardService dùng repository projection để lấy thống kê: tổng user active, tổng đơn hợp lệ, tổng doanh thu đã thanh toán, đơn pending, biểu đồ doanh thu theo ngày, top sản phẩm bán chạy và doanh thu theo danh mục.

4.8 Tích hợp AI từ Spring Boot

AiController expose endpoint /api/ai/chat và /api/ai/recommend. AiService gọi sang Flask bằng RestTemplate, nhận danh sách product id, sau đó fetch lại sản phẩm trong database Spring để trả về ProductResponse đầy đủ và chỉ giữ SKU còn hàng.

6. Thuật toán AI, RAG, recommendation

6.1 LLM router trong agent_service

agent_service.py dùng LLM như một orchestrator. LLM đọc câu hỏi người dùng, sau đó trả JSON để chọn một trong ba tool: search_products, chat_with_bot, hoặc get_recommendations. Temperature bằng 0.0 để output ổn định.

User message -> LLM router -> JSON: {"tool": "...", "arguments": {...}} -> Python executor gọi đúng service -> Lấy product context từ DB -> LLM sinh câu trả lời -> Stream về client bằng SSE

6.2 Intent extraction trong intent_service

Service trích xuất các slot quan trọng của nhu cầu mua hàng: từ khóa tìm kiếm, ngân sách tối đa, danh mục, brand, môn thể thao, giới tính, màu mong muốn, phân khúc giá và từ khóa loại trừ.

Slot Ví dụ Cách dùng
search_keywords "giày Nike chạy bộ nam" Tạo enhanced query để embedding và lexical search.
max_budget 1000000 Lọc SQL với dung sai ngân sách 15%.
category_id 1 = giày, 2 = quần áo, 3 = phụ kiện Lọc cứng theo danh mục nếu đủ tin cậy.
brand_name Nike, Adidas, Puma Lọc brand, có alias tiếng lóng như "nai", "das", "ua".
excluded_keywords ["đen", "xám"] Loại bỏ sản phẩm chứa từ khách không muốn.

Khi LLM lỗi, hệ thống fallback regex: bắt giá theo "triệu", "củ", "k", nhận diện màu phủ định, brand alias, category và sport type. Điều này giúp service không chết khi API AI gặp lỗi.

6.3 Embedding và chunking

embedding_service.py dùng model multilingual-e5-large-instruct. Text dài được cắt thành chunk dưới giới hạn token, có overlap 40 token để giữ ngữ cảnh. Nếu một sản phẩm có nhiều chunk, vector cuối được tính bằng trung bình có trọng số token và normalize.

Embedding text dài: 1. Clean text 2. Split thành chunks theo câu hoặc token window 3. Embed từng chunk 4. Weighted average theo số token 5. Normalize vector

6.4 Hybrid RAG search trong rag_service

Tìm kiếm không chỉ dùng vector thuần. Pipeline kết hợp LLM intent, vector search, lexical search, broad fallback và reranking. Đây là điểm mạnh vì truy vấn tiếng Việt ngắn/dài, có giá, màu, brand, phủ định đều được xử lý.

Giai đoạn 0: analyze_query(query) -> Lấy intent: keywords, budget, brand, category, color, excluded Giai đoạn 1: candidate retrieval -> Enhanced query -> embedding -> pgvector cosine search -> Lexical search bằng LIKE và score theo tên/thuộc tính/danh mục/mô tả -> Merge candidate, loại trùng -> Nếu không có, broad fallback theo dữ liệu mới/còn hàng Giai đoạn 2: rerank -> Tính vector_score, lexical_score, keyword_score, personalization -> Boost màu, profile/body fit, review -> Trừ penalty từ hủy/trả/đánh giá xấu -> Sort final_score giảm dần
Rerank search: vector_score = max(0, 1 - cosine_distance / 2) lexical_score = lexical_score_raw / max_lexical keyword_score = matched_keywords / total_keywords final_score = 0.42 * vector_score + 0.28 * lexical_score + 0.15 * keyword_score + 0.15 * personalization + boost

6.5 RAG chatbot multi-turn

chatbot_service.py lưu session và message vào database. Mỗi lượt chat, service truy xuất sản phẩm liên quan bằng RAG, lấy thêm personalization context nếu có user, load 6 tin nhắn gần nhất, rồi gọi LLM để sinh câu trả lời.

Chat flow: 1. Tạo hoặc kiểm tra session 2. Lưu tin nhắn USER 3. search_similar_products(message, top_k=4) 4. Nếu câu hỏi về body/sở thích: merge thêm recommendation 5. Lấy thông tin sản phẩm còn hàng 6. Build prompt: system + sản phẩm + cá nhân hóa + history 7. LLM sinh reply tối đa 3-4 câu 8. Lưu tin nhắn BOT và retrieved_product_ids

6.6 Recommendation engine

recommendation_service.py dùng hướng content-based + behavior-based + popularity fusion. Hệ thống lấy seed từ nhiều nguồn: đơn hàng, wishlist, cart, user interaction, review, lịch sử trạng thái đơn, yêu cầu trả hàng, sản phẩm từng xuất hiện trong chatbot. Mỗi tín hiệu có trọng số và time decay.

Nguồn tín hiệu Trọng số/ý nghĩa
Đơn đã giao/thành công Tín hiệu mạnh nhất, thể hiện sở thích thật.
Thêm giỏ hàng Tín hiệu quan tâm cao.
Wishlist Tín hiệu yêu thích, chưa mua.
View/Search Tín hiệu nhẹ, giúp hiểu hành vi duyệt sản phẩm.
Review tốt/xấu Review tốt tăng điểm; review xấu hoặc trả hàng/hủy đơn tạo penalty.
Chiều cao/cân nặng Tính BMI/ước lượng size, boost sản phẩm quần áo phù hợp.
Time decay: signal = base_weight * exp(-age_seconds / (86400 * 45)) Ý nghĩa: hành vi càng mới càng có trọng số cao; sau khoảng 45 ngày tín hiệu giảm đáng kể.
Weighted centroid: centroid = mean(seed_embedding_i * normalized_weight_i) Sau đó dùng pgvector tìm sản phẩm gần centroid nhất, loại sản phẩm đã mua thành công và chỉ lấy sản phẩm active/còn hàng.
Rerank recommendation khi brand đáng tin cậy: final_score = 0.32 * vector_score + 0.20 * behavior_score + 0.08 * behavior_candidate_score + 0.14 * review_score + 0.10 * recency_score + 0.04 * popularity_score + 0.12 * body_fit_score - penalty

6.7 Cold start

Nếu user chưa có hành vi hoặc seed không có embedding, recommendation fallback sang sản phẩm phổ biến, còn hàng, active và phù hợp profile nếu có. Đây là cách xử lý bài toán cold start.

7. Luồng tích hợp giữa hai service

Spring gọi Flask

Frontend có thể gọi Spring Boot /api/ai/chat hoặc /api/ai/recommend. Spring sẽ lấy user hiện tại bằng JWT, gọi Flask AI service, nhận danh sách product id, rồi tự fetch sản phẩm bằng repository của Spring. Cách này giúp response cuối cùng thống nhất với DTO của hệ thống chính.

Frontend -> Spring /api/ai/chat Spring AiController: request.setUserId(currentUserId) -> AiService.processChat -> POST Flask /api/ai/chat Flask: -> RAG + LLM + DB -> trả reply + product_ids Spring: -> fetch ProductResponse theo product_ids -> lọc SKU active và còn hàng -> trả ApiResponse cho frontend

Dữ liệu dùng chung

  • Cả hai service dùng cùng PostgreSQL database datn.
  • Spring quản lý dữ liệu nghiệp vụ: users, products, orders, carts, reviews.
  • Flask đọc các bảng đó để tạo context và gợi ý; đồng thời đọc/ghi bảng chatbot và embedding.
  • pgvector nằm trong PostgreSQL nên không cần vector database riêng.

Lợi ích kiến trúc tách service

Dễ mở rộng

Có thể scale AI service riêng vì việc gọi LLM/embedding nặng hơn nghiệp vụ CRUD thông thường.

Dễ thay model

Có thể đổi model embedding hoặc LLM trong Flask mà không ảnh hưởng lớn đến Spring Boot.

Tách trách nhiệm

Spring giữ vai trò nguồn dữ liệu và luật nghiệp vụ; Flask tập trung vào xử lý AI.

Khả năng fallback

Nếu AI lỗi, Spring vẫn có thể trả lỗi thân thiện hoặc giữ các chức năng bán hàng cốt lõi hoạt động.

8. Gợi ý trả lời bảo vệ

1. Vì sao dùng Spring Boot cho backend chính?

Vì Spring Boot phù hợp xây dựng REST API lớn, có sẵn Spring Security, Data JPA, transaction, validation, mail, OAuth2. Dự án có nhiều nghiệp vụ thương mại điện tử cần transaction chặt chẽ, nên Java/Spring giúp code rõ lớp và an toàn dữ liệu.

2. Vì sao tách AI thành Flask service?

AI có dependency Python, model embedding, LangChain và thư viện ML riêng. Tách thành service riêng giúp thay model, scale và debug AI độc lập, trong khi Spring Boot vẫn giữ nghiệp vụ chính ổn định.

3. RAG trong dự án hoạt động thế nào?

RAG là Retrieval-Augmented Generation. Đầu tiên hệ thống phân tích intent từ câu hỏi, tạo embedding và tìm sản phẩm liên quan bằng pgvector, kết hợp lexical search để tránh miss keyword, sau đó rerank ứng viên và đưa thông tin sản phẩm còn hàng vào prompt để LLM trả lời.

4. Vì sao không chỉ dùng LIKE search?

LIKE search chỉ khớp từ khóa trực tiếp, khó hiểu các câu tự nhiên như "giày nhẹ để chạy dưới 1 triệu". Vector search hiểu ngữ nghĩa tốt hơn. Tuy nhiên vector search có thể bỏ sót từ khóa chính xác, nên dự án kết hợp cả vector và lexical search.

5. Recommendation cá nhân hóa dựa trên gì?

Dựa trên nhiều tín hiệu: mua hàng, giỏ hàng, wishlist, view/search, review, lịch sử chat, trả/hủy hàng và thông tin chiều cao/cân nặng. Các sản phẩm seed được lấy embedding, tính centroid có trọng số, tìm sản phẩm tương tự rồi rerank bằng review, độ mới, popularity và body fit.

6. Dự án xử lý thiếu hàng khi nhiều người cùng đặt như thế nào?

Khi đặt hàng, service không chỉ check tồn kho trước mà còn trừ kho bằng update có điều kiện stockQuantity >= qty. Nếu update không ảnh hưởng dòng nào thì báo thiếu hàng và rollback transaction. Cách này giảm rủi ro bán vượt tồn kho.

7. Vì sao cần DTO và mapper?

DTO giúp tách dữ liệu API khỏi entity database, tránh lộ dữ liệu nhạy cảm và tránh vòng lặp quan hệ khi serialize. Mapper giúp chuẩn hóa cách chuyển đổi entity sang response.

8. Điểm mạnh kỹ thuật của dự án là gì?

Điểm mạnh là kết hợp được backend thương mại điện tử đầy đủ với AI thực tế: JWT/OAuth2, transaction đơn hàng, VNPAY, ví, dashboard, SKU/attribute động, chatbot RAG, vector search và recommendation cá nhân hóa.

Checklist kiến thức nên nắm

  • Giải thích được mô hình Controller -> Service -> Repository -> Entity.
  • Giải thích được Product, SKU, AttributeValue khác nhau thế nào.
  • Giải thích được flow đặt hàng, tính tiền, coupon, trừ kho và thanh toán.
  • Giải thích được JWT access token, refresh token và role claims.
  • Giải thích được RAG: intent -> embedding -> vector search -> rerank -> LLM.
  • Giải thích được pgvector và cosine distance <=>.
  • Giải thích được weighted centroid và time decay trong recommendation.
  • Biết nêu ưu/nhược điểm: AI phụ thuộc API ngoài, reranker còn heuristic, cần caching và monitoring nếu triển khai thật.
